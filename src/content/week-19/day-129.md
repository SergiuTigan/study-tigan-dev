## The Work

### Category 1: RAG & Retrieval (30 min)

Prepare answers for:

**"How would you evaluate a RAG system?"**
> Measure retrieval quality (precision/recall of retrieved chunks), generation quality (faithfulness to context, relevance to query), and end-to-end quality (answer correctness). Use both automated metrics (LLM-as-judge, RAGAS framework) and human evaluation for edge cases.

**"What affects RAG quality the most?"**
> Chunking strategy (size, overlap, method), embedding model quality, retrieval parameters (top-k, similarity threshold), and prompt design for the generation step. In my experience, chunk size had the biggest impact — going from 1000-token chunks to 500-token chunks improved retrieval accuracy by 15%.

**"When would you NOT use RAG?"**
> When the knowledge base is small enough to fit in context, when the information changes faster than you can re-index, when the query doesn't require grounding in specific documents, or when latency requirements are extremely tight (RAG adds retrieval overhead).

### Category 2: Agents & Tool Use (25 min)

**"What's the difference between an agent and a workflow?"**
> A workflow has a predetermined sequence of steps. An agent dynamically decides its next step based on previous results. Workflows are more predictable and easier to debug. Agents are more flexible but harder to control. Use workflows when the process is known; use agents when the path depends on input.

**"How do you prevent hallucinations in agent loops?"**
> Ground the agent in retrieved data (RAG), validate tool outputs against expected schemas, set maximum iteration limits, add guardrails on output (content filters, format validation), and use structured output to constrain the response format.

**"How do you decide what tools to give an agent?"**
> Start minimal — only tools the agent needs for its core task. Each tool should have a clear, distinct purpose. Test whether the agent correctly selects tools. If it misuses a tool frequently, the tool description is ambiguous or the tool shouldn't be available.

### Category 3: Prompt Engineering (25 min)

**"How do you design a production prompt?"**
> Start with role and context, define the output format explicitly, include constraints and edge case handling, add few-shot examples if consistency matters, version control the prompt, and test against a diverse set of inputs before deploying.

**"Design a prompt for summarizing customer support tickets."**
> Walk through: system role ("You are a support ticket summarizer"), input format, output format (structured: category, priority, summary, action items), constraints (max length, required fields), and edge cases (empty tickets, multiple issues in one ticket).

**"How do you handle prompt injection?"**
> Separate system instructions from user input, use delimiter tokens, validate and sanitize user input, use a secondary LLM call to check for injection attempts, implement output filtering, and never expose system prompts to users.

### Category 4: Evaluation & Testing (20 min)

**"How do you test an LLM application?"**
> Unit tests for deterministic logic, integration tests for API calls, eval suites with diverse test cases for AI output quality, regression tests when changing prompts or models, and human evaluation for subjective quality. I use LLM-as-judge for scalable evaluation.

**"How would you detect model quality degradation?"**
> Run a fixed eval suite on every prompt change or model update, track quality metrics over time, set up alerts for metric drops, maintain a "golden set" of test cases with expected outputs, and periodically sample production outputs for human review.

### Category 5: Cost & Production (20 min)

**"How do you optimize LLM costs?"**
> Model routing (cheap model for simple queries, expensive for complex), caching common responses, reducing context window size, batching where possible, using smaller models for classification/routing, and monitoring cost-per-query metrics.

**"What's your deployment strategy for AI apps?"**
> Vercel for the web app, environment variables for API keys (never in code), monitoring for latency and error rates, cost tracking per endpoint, gradual rollout for prompt changes, and fallback behavior when the AI provider is down.

**"How do you handle AI provider outages?"**
> Fallback to a secondary provider (e.g., OpenAI → Anthropic), cached responses for common queries, graceful degradation (show the app works without AI, even if limited), retry with exponential backoff, and clear user communication.
